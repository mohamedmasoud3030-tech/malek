# مواصفة الأحداث المحاسبية النظامية — بدون تنفيذ

**الحالة:** توثيقي فقط. هذه مواصفة (spec)، وليست SQL أو Migration جاهزة للتنفيذ.
**يعتمد على:** `ACCOUNTING_DECISION_GATES_AR.md` (C1–C11)، `CONTRACT_RIGHTS_AND_ACCOUNTING_MATRIX_AR.md`.

كل حدث أدناه موصوف بالحقول المطلوبة. حيث يكون القرار المرتبط محجوبًا (BLOCKED)، يُذكر ذلك صراحة بدلاً من افتراض معالجة.

## 1. إنشاء فاتورة إدارة عقار

| الحقل | القيمة |
|---|---|
| الشرط التجاري | عقد نشط + دورة فوترة مستحقة (`generate_invoices_from_active_contracts`) |
| المستند المصدر | `contracts` + `owner_agreements` |
| المسؤول عن الاعتماد | نظام آلي (scheduled) — لا يتطلب اعتماد بشري حسب التصميم الحالي |
| Subledger / GL / كلاهما | **Subledger فقط** (راجع C1 — لا قيد GL عند الإصدار) |
| وقت الاعتراف | لحظة إصدار الفاتورة في `invoices` |
| الحساب المدين | لا ينطبق (لا قيد GL) |
| الحساب الدائن | لا ينطبق (لا قيد GL) |
| المصدر المحاسبي للمبلغ | `contracts.rentAmount` × عامل التناسب حسب `billing_basis` (C4) |
| VAT | حسب `vat_treatment` — معطّل افتراضيًا (0001) |
| التقريب | 3 خانات عشرية (OMR) — راجع تعارض C7 غير المحسوم |
| company_id / owner_id / property_id / contract_id / invoice_id | جميعها مطلوبة كحقول ربط قياسية |
| مفتاح عدم التكرار | `(contract_id, billing_period)` متوقع، يحتاج تأكيد schema فعلي |
| كيفية العكس | إلغاء الفاتورة (`cancelled` status) — يتطلب توثيق ما إذا كان الإلغاء بعد بدء التحصيل الجزئي مسموحًا |
| أثر الفترة المقفلة | **BLOCKED — C6 محجوب بالكامل**، لا سياسة حالية |
| تقرير المصالحة | لا ينطبق (Subledger event فقط) |

## 2. تحصيل إيجار (Payment/Receipt)

| الحقل | القيمة |
|---|---|
| الشرط التجاري | دفعة مسجّلة عبر `record_invoice_payment_atomic` / `post_receipt_atomic` |
| المستند المصدر | `payments`, `receipts` |
| المسؤول عن الاعتماد | المستخدم المخوّل (Accountant/Manager حسب صلاحيات 0003) |
| Subledger / GL / كلاهما | **كلاهما** — يُحدّث `invoices.status` (Subledger) وينشئ `journal_entries` (GL) في نفس المعاملة الذرية |
| وقت الاعتراف | لحظة التحصيل الفعلي (نقدي بالكامل، حسب 0001 والأساس النقدي) |
| الحساب المدين | Cash / Bank |
| الحساب الدائن | حسب C1: `Owner Funds Payable` (إذا OWNER_IS_CREDITOR — الافتراض المرجّح) أو `Tenant Receivable` (إذا OFFICE_IS_CREDITOR — يتطلب `collection_role`) |
| المصدر المحاسبي للمبلغ | `payments.amount` الفعلي المُدخل |
| VAT | لا ينطبق على التحصيل نفسه؛ ينطبق على الفاتورة الأصلية إن كان مفعّلاً |
| التقريب | 3 خانات عشرية |
| الحقول القياسية | جميعها مطلوبة + `payment_id` |
| مفتاح عدم التكرار | `request_id` (مؤكد فعليًا من ADR 0005 — idempotency fingerprint) |
| كيفية العكس | VOID عبر `void_receipt_atomic` — ينشئ قيد عكس، **لا يحذف** (مؤكد من ADR 0005 و0003) |
| أثر الفترة المقفلة | BLOCKED — C6 |
| تقرير المصالحة | `Tenant Receivable Subledger = GL Due from Owners` (إذا OFFICE_IS_CREDITOR فقط — راجع القسم سابعًا) |

## 3. إثبات عمولة RATE

| الحقل | القيمة |

## 4. استحقاق رسم FIXED_MONTHLY

| الحقل | القيمة |
|---|---|
| الشرط التجاري | راجع C2 — **APPROVED WITH CONTRACT CONDITION**؛ الافتراض الحالي هو نفس شرط RATE (عند التحصيل)، ما لم ينص عقد بخلاف ذلك |
| المستند المصدر | `owner_agreements.fixedFee` + `billing_basis` (C4) |
| المسؤول عن الاعتماد | آلي |
| Subledger / GL / كلاهما | كلاهما (بنفس منطق RATE) |
| وقت الاعتراف | عند التحصيل (افتراضي)، **مع علم أن هذا يحتاج تأكيدًا صريحًا من صاحب النظام إن كانت الرسوم الثابتة يجب أن تُستحق زمنيًا بدلاً من نقديًا** |
| الحساب المدين/الدائن | نفس RATE أعلاه |
| المصدر المحاسبي للمبلغ | `fixedFee` مُعدَّل بعامل `billing_basis` (FULL_MONTH أو DAILY_PRORATED حسب C4) |
| كيفية العكس | نفس منطق العكس التلقائي المرتبط بعكس الدفعة |

## 18. استرداد بعد دفع المالك

| الحقل | القيمة |
|---|---|
| السبب في التحويل إلى Due from Owner بدل جعل Owner Payable سالبًا | لأن `Owner Payable` سالب يعني محاسبيًا أن المكتب مدين للمالك بمبلغ لا أساس تعاقدي واضح له بعد — بينما `Due from Owner` يمثّل **ذمة مستقلة وصريحة** تحتاج قرار تحصيل منفصل (C8)، ولا تُخفى داخل رصيد التسوية العادي. هذا يحافظ على وضوح القوائم المالية (C10 — لا دمج مقاييس مختلفة المعنى) |
| الحالة | APPROVED (كمبدأ توجيه) — التنفيذ الفعلي محجوب بانتظار C8 الكامل |

## 19–22. عمولة الوسيط (إنشاء/اعتماد/دفع/عكس)

**الحالة: BLOCKED BY MISSING DATA بالكامل للأربعة أحداث.** الوحدة موصوفة رسميًا في `DOMAIN.md` كـ "tracking view... not a full payout/accounting module" ولا ربط مؤكد بـ `journal_entries` أو `expenses`. لا يمكن كتابة مواصفة قيد دقيقة دون تصميم مخصص جديد لهذه الوحدة أولاً.

---

## 23–27. Master Lease (بداية/دفعة/إهلاك/فائدة/إيراد تأجير فرعي)

**الحالة: BLOCKED BY LEGAL REVIEW + BLOCKED BY MISSING DATA بالكامل للخمسة أحداث** — راجع C5. لا معنى لكتابة قيود GL محددة لأصل حق استخدام أو التزام إيجار أو إهلاك أو فائدة قبل حسم التصنيف المحاسبي للعقد نفسه (تشغيلي أم تمويلي) وتصميم schema مخصص. كتابة قيود افتراضية هنا الآن تُخاطر بإثبات نموذج محاسبي خاطئ يصعب التراجع عنه لاحقًا.
