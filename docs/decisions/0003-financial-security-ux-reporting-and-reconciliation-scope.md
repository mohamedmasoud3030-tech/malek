# 0003. Financial security, UX, reports, and bank reconciliation release scope

## Context
Readiness blockers remained around the financial golden path, operation-level permissions, mobile/RTL acceptance, required reports/statements, and bank reconciliation scope.

## Decision
The approved financial golden path is `invoice -> payment -> receipt -> void receipt/payment -> report proof -> statement proof -> audit proof`. Cash and bank transfer must be fully supported; online payment may be supported or simulated depending on available integrations. Voiding requires a reason, never deletes history, returns net report totals to the correct effect, updates invoice status to unpaid or partial as applicable, updates tenant and owner statements immediately, and writes audit evidence. CSV/PDF or print proof is required for core reports, with a rounding tolerance of 0.01 currency units per transaction/report total.

The approved roles are Admin, Manager, Accountant, Viewer, Owner, and Tenant. Admin has all permissions. Manager may create invoices, record payments, export operational reports, and manage tenants/contracts within the organization, but may not void receipts, approve/pay settlements, or give final bank-reconciliation approval unless explicitly granted. Accountant may create invoices, record payments, void with reason, manage settlements, reports, reconciliation, and financial adjustments according to assigned permissions. Viewer is read-only. Owner and Tenant portal users are future read-only scoped roles. Report export and bank match/unmatch/approval require separate permissions. Every financial action requires audit logging, denied actions should show “You do not have permission to perform this action.”, RLS must prevent cross-organization access, and super admin is a break-glass audited role only.

Arabic RTL is the primary launch language. English must not break, but full English completeness may be phased later if it delays readiness. Manual mobile acceptance focuses on login, dashboard, tenants/contracts, invoices/payments/receipts, and reports/owner statement/tenant statement across iPhone/Safari, Android/Chrome, desktop Chrome/Chromium, and tablet/iPad as an additional check. Baseline screenshots are required for core screens. Critical workflows need keyboard usability and basic axe scans, with WCAG AA as a progressive target. Financial tables must be responsive or have clear horizontal scrolling. Print/export layout is part of acceptance for core reports/statements.

Launch-required reports are daily collections, overdue invoices, aged receivables, income statement, balance sheet, trial balance, rent roll, owner statement, tenant statement, settlement report, and bank reconciliation report if reconciliation is in release scope. Every report needs CSV export; PDF/print is required for owner statement, tenant statement, daily collections, income statement, and settlement report. Owner statements must show rent collected, office fees, maintenance deductions, utility/owner expenses, settlement payments, and opening/closing balances. Tenant statements must show invoices, payments, deposits, utilities, maintenance charges, relevant credits/refunds/voids, and running balance. Every report needs date-range filtering and multi-property filtering. Rounding is line-level with clear totals and explicit rounding adjustments if needed. Voided payments remain in audit and may appear as voided transactions or be excluded from totals with an include-voided option.

Bank reconciliation launch scope is CSV and XLSX import, with OFX later if needed and MT940 only if a specific bank requires it. Each bank may have a distinct mapping. The import wizard must support upload, mapping, preview, duplicate detection, and import. Duplicate detection uses bank account, transaction date, amount, reference/description, balance if available, and import batch/hash. Matching starts with manual and suggested matching; auto-match is permitted only for high-confidence cases and should initially behave as a suggestion rather than automatic posting. Matching rules include amount, a date window such as +/-3 days, reference, receipt/invoice number, tenant/payer name, and bank description. Unmatch requires reason and audit log. Reconciliation needs approval/close before final status. Reconciliation adds bank-verified status and must not change financial totals without an explicit transaction adjustment.

## Alternatives rejected
Treating frontend permission hiding as sufficient authorization was rejected because backend RLS/RPC/grant proof is still required. Running mobile acceptance only on desktop emulation was rejected. Releasing reports without export/print evidence was rejected for the required statement and financial report set. Auto-posting bank matches by default was rejected in favor of suggested/manual matching first.

## Consequences
Upcoming implementation phases must build backend permission enforcement and audit proof, expand Playwright/manual evidence beyond unauthenticated smoke, complete report/export coverage, and implement reconciliation import/matching as an auditable workflow. The scope is now decided, but code, schema, live verification, and release evidence remain required before readiness claims.
