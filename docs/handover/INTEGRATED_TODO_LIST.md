## 🚀 المرحلة 1 — التحقق التشغيلي الحي قبل الإطلاق

**الحالة: تبدأ بعد إغلاق Data Contract Stabilization لـDeposits وAutomation على Staging.**  
هذه المرحلة لا تعيد تطوير الميزات؛ هدفها إثبات أن النسخة المدمجة تعمل على البيئة المستهدفة دون فقد بيانات أو اختلاف Schema.

### 1.1 قاعدة البيانات والإصدارات

- [ ] أخذ نسخة احتياطية قابلة للاستعادة قبل أي تطبيق على Production.
- [ ] تطبيق migrations المدمجة على بيئة Staging مرتبطة فعليًا بالمشروع.
- [ ] مقارنة migration ledger المحلي مع البيئة المستهدفة والتأكد من عدم وجود drift أو migrations يتيمة.
- [ ] التحقق حيًا من وجود `pg_cron` ونجاح job باسم `rentrix-automation-hourly`، أو توثيق البديل المجدول إذا كانت الإضافة غير متاحة.
- [ ] قراءة تعريفات RPCs الحساسة حيًا ومقارنتها بالمصدر المدمج، خصوصًا:
  - `record_invoice_payment_atomic`
  - `void_receipt_atomic`
  - RPCs التأمينات
  - RPCs تسويات الملاك
  - `rpt_daily_collection`

### 1.2 دورة تشغيل مالية كاملة على Staging

- [ ] تسجيل الدخول بحسابات `ADMIN` و`MANAGER` و`USER` واختبار حدود الصلاحيات الفعلية.
- [ ] إنشاء مالك → عقار → وحدة → مستأجر → عقد.
- [ ] توليد فاتورة للعقد.
- [ ] تنفيذ دفعة جزئية ثم دفعة كاملة.
- [ ] إنشاء سند قبض ثم تنفيذ `VOID` والتحقق من القيد العكسي.
- [ ] التحقق من تطابق الفواتير والمدفوعات والإيصالات والتخصيصات والقيود والأرصدة والتقارير.
- [ ] تنفيذ دورة وديعة كاملة: استلام → خصم جزئي → استرداد → تسوية نهائية، مع اختبار منع تجاوز الرصيد.
- [ ] تنفيذ تسوية مالك: إنشاء/قراءة → اعتماد → دفع، والتحقق من journal والأرصدة.

### 1.3 Storage وBackup/Restore

- [ ] رفع مستند حقيقي إلى bucket `attachments` الخاص.
- [ ] التأكد أن المعاينة والتنزيل يعملان عبر signed URL فقط وأن الرابط ينتهي حسب TTL.
- [ ] إثبات أن مستخدمًا غير مصرح لا يستطيع قراءة الملف مباشرة.
- [ ] تنفيذ Restore فعلي إلى قاعدة Staging منفصلة والتحقق من الجداول والأرصدة وعدد السجلات.
- [ ] توثيق RPO/RTO وخطوات الاسترجاع ومسؤول التنفيذ.

### 1.4 النشر والتحقق النهائي

- [ ] تأكيد متغيرات Production في Vercel دون طباعة أو تخزين Secrets في git/logs.
- [ ] التحقق من أن production env guard يرفض placeholders ويقبل القيم الحقيقية.
- [ ] تشغيل smoke نهائي على رابط النشر بعد تطبيق migrations.
- [ ] اختبار المقاسات `360 / 390 / 430 / 768 / 1440` مع RTL وlight/dark.
- [x] التأكد من عدم وجود open PRs تخص الإصدار؛ GitHub يعرض حاليًا صفر PRs مفتوحة. Review Threads والفروع المتقادمة تحتاج مراجعة مستقلة عند كل إصدار.
- [ ] إصدار قرار Go/No-Go مكتوب بأدلة التنفيذ الحية.

### شروط قبول المرحلة 1

لا تُغلق المرحلة إلا عند تحقق الآتي:

- [ ] لا فقد بيانات في دورة النسخ والاستعادة.

## قواعد التنفيذ

1. كل مرحلة تُنفذ وتُوثق وتُغلق قبل بدء المرحلة التالية.
2. لا تُعاد كتابة Audit جديد بدل التنفيذ.
3. لا تُعلن مهمة مكتملة دون دليل CI أو Staging/Production مناسب لطبيعتها.
4. لا تُطبّق تغييرات مالية أو أمنية مباشرة على Production دون Backup وخطة رجوع.
5. المانع الحقيقي للإطلاق يقتصر على: فقد البيانات، فشل المصادقة، تعطل العقود أو التحصيل، خطأ مالي جسيم، أو ثغرة أمنية حرجة.
6. التحسينات الشكلية والـrefactor غير المانعة تبقى في مرحلة ما بعد الإطلاق.
