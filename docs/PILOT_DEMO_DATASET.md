# MALEK Pilot Demo Dataset

Status: READY FOR QA/PRESENTATION SEEDING

## Purpose

This dataset gives the first MALEK office / sales presentation a realistic operating picture without bypassing the product's accounting controls.

The dataset is intentionally created through the same governed runtime commands used by the application for contracts, invoice generation, collections, and expenses. `supabase/seed.sql` remains reference/bootstrap-only.

## Dataset shape

The deterministic `malek-pilot-demo-v1` dataset creates one isolated demo company with:

- 3 owners.
- 3 properties in Muscat and Sohar.
- 6 units, including one intentionally vacant unit.
- 5 tenants.
- 5 maker/checker-approved, activated long-term contracts.
- Current-period rent invoices generated by `generate_invoices_from_active_contracts`.
- Full collection, partial collection, and unpaid scenarios.
- Owner-responsibility maintenance/service expenses.
- A company-responsibility operating expense that must not reduce an owner's payout.

Financial mutations use the canonical RPC layer. The script does not insert payments, receipts, journal entries, or expenses directly.

## Safety contract

`rentrix-app/scripts/pilot-demo-seed.mjs` is mutation-capable and therefore fails closed unless all required environment values are present.

It currently allows only:

- `PILOT_ENVIRONMENT_KIND=local`
- `PILOT_ENVIRONMENT_KIND=qa`

For hosted QA, `QA_SUPABASE_PROJECT_REF` must exactly match `VITE_SUPABASE_URL` and `QA_MUTATION_APPROVED=1` must be explicitly set. The script also receives `PRODUCTION_SUPABASE_PROJECT_REF` and refuses to run when the target host matches Production.

This separation is deliberate: prove the dataset on the dedicated QA/presentation stack first. Promoting the same presentation dataset into the production project is a separate controlled release action, not an accidental consequence of running a local command.

## Run

From the repository root:

```bash
PILOT_ENVIRONMENT_KIND=qa \
QA_MUTATION_APPROVED=1 \
pnpm pilot:seed
```

Credentials and project references are supplied from the secret runtime. Never commit them.

## Expected verification

The script verifies, at minimum:

- 3 properties
- 6 units
- 3 owners
- 5 contracts
- 5 generated invoices
- at least 2 receipts
- at least 3 expenses

It prints a JSON evidence summary including the dataset tag, company id, counts, scenario list, target environment, and verification timestamp.
